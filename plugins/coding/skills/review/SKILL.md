コードの差分をレビューする。**実際にgit状態を変更する操作(checkout/merge/commit/push/add/stashなど)や、PRへのコメント投稿・approve・mergeなどは一切行わない。行うのは既存の状態の読み取り(diff/status/show、PRの閲覧)のみ。**

## レビュー種別を判定する

依頼内容から、以下のいずれかを判定する。判断がつかない場合はユーザーに確認する(推測で決めない)。特に「PRの差分を確認して」のようにPR番号もマージ先ブランチも無い依頼は、既存PRのレビューか、PRを出す前提のブランチ間差分レビューかを確認する。

- **PRレビュー**: GitHub上に既に存在するPRの差分とコメントをレビューする。`$target` がPR番号(`123` / `#123`)またはPRのURLの場合、または「このブランチのPRをレビューして」のように既存PRを指している場合。
  → 詳細手順は同階層の `pr-review.md`(`${CLAUDE_SKILL_DIR}/pr-review.md`)を参照して従う。

- **ブランチ間差分レビュー**: 現在のブランチ(マージ元)から指定したブランチ(マージ先)へPRを作成したと**仮定**した場合の差分をレビューする。マージ先ブランチが分かっている/指定されている、または「マージ前チェック」のように依頼されている場合。
  → 詳細手順は同階層の `branch-diff.md`(`${CLAUDE_SKILL_DIR}/branch-diff.md`)を参照して従う。

- **未コミット変更レビュー**: 現在の作業ツリーにある、まだコミットしていない変更(staged/unstaged/untrackedファイル)をレビューする。マージ先ブランチやPRの指定がなく、「今の変更を見て」「コミット前にレビューして」のように依頼されている場合。
  → 詳細手順は同階層の `uncommitted-diff.md`(`${CLAUDE_SKILL_DIR}/uncommitted-diff.md`)を参照して従う。

## 全レビューに共通する事項

- 同梱スクリプトは `uv run ${CLAUDE_SKILL_DIR}/<script>.py ...` で実行する（PEP 723 のメタデータで依存の `pathspec` が自動で入る）。uv が無い環境では `python` に置き換え、`.diffignore` を使うなら `pathspec` を入れておく。
- 差分取得スクリプトは読み取り専用のコマンドのみを使う(ブランチ間/未コミットは git、PRは gh)。`git fetch` もしない。
- 差分は `temp/review/` 配下に出力される。分割ファイルが複数生成された場合は、まず `INDEX.md` を読んで全体像(ファイル別のstatus/行数)を把握してから、必要な `diff_XXXX.diff` だけを個別に読む。1ファイルのみで済んだ場合は標準出力に差分本文がそのまま出るため、追加でファイルを読む必要はない。
- 1ファイルの差分が2000行を超えると「巨大」とみなし、単独の `diff_XXXX.diff` に隔離して `INDEX.md` に `⚠ 巨大` と印を付ける。生成物・スナップショット・ロックファイルなら本文は読まず、パスと行数だけ報告に含める。手書きのコードなら分けて読む。
- 同階層の `.diffignore` に記載したパターン(`.gitignore` と同じ書式)にマッチするファイルは、レビュー対象から自動的に除外される。`.diffignore` は gitignore 済みで、雛形は `.diffignore.example`(ロックファイル・スナップショットの例入り)。
- サブモジュールのポインタ変更は、差分ブロックにサブモジュール内のコミット一覧と「新しい commit がリモートのどこかのブランチにあるか」を出す(ブランチ間差分レビュー)。`⚠ リモートのどのブランチにも無い` は未push の疑いなので、blocker として報告する(手元の remote-tracking 情報に基づくので、古ければ fetch を勧める)。
- 古い出力はスクリプトが消さない。`temp/review/` の中身はレビューが終われば不要なので、溜まっていればユーザーに削除を提案する(自分では消さない)。

## レビュー観点

各ブロックの数値列(`original_lines` / `new_lines`、PRレビューでは `additions` / `deletions`)は変更規模の把握に使う。差分を読むときは次を確認する。該当しない項目は飛ばしてよい。

- **正しさ**: バグ、境界条件、エラー処理、既存動作への影響
- **テスト**: 変更に対応するテストがあるか。関連するテストを実行できるなら実行し、実行したコマンドと結果を報告する(読み取り専用の範囲で。テストが作業ツリーを書き換える場合は実行前にユーザーに確認する)
- **生成物**: 生成元を変えたのに生成物が更新されていない、または生成物だけが手で直されている
- **混入**: 意図しないファイル、デバッグ用のコード、秘密情報(トークン・鍵・`.env` の実体)
- **サブモジュール**: ポインタ先がリモートに無い、意図しない巻き戻し
- **ドキュメント**: 挙動・使い方を変えたのに README・ドキュメントが古いまま
- **一貫性**: 命名・スタイル・既存の規約(リポジトリの AGENTS.md / CONTRIBUTING.md 等)との不一致

## 結果の報告

指摘は重大度を付けて、重いものから並べる。

- **blocker**: マージ前に必ず直す(バグ、秘密情報、未push のサブモジュール、CI が落ちる変更など)
- **should**: 直したほうがよい(テスト不足、ドキュメントの更新漏れ、分かりにくい実装)
- **nit**: 好みの範囲(命名、細かいスタイル)

各指摘には `パス:行` と、何が起きるか(具体的な入力・状況)を書く。指摘が無い観点は「確認したが問題なし」とまとめてよい。

あわせて以下を明記する。

- どの種別のレビューか、および状態を変更する操作は行っていないこと
- 比較した ref(ブランチ間差分なら `origin/<target>` かローカルの `<target>` か、merge-base)
- 差分ファイルの出力先ディレクトリのパス
- `.diffignore` によって除外されたファイル・巨大として本文を読まなかったファイルがあれば、その件数とパス
- 実行したテストのコマンドと結果

## PR 作成へのつなぎ

review は PR を作らない。レビュー後に PR を作るなら `pr-check` スキルを使う。そのとき、上の報告のうち「実行したテスト」「確認した観点」「残っている注意点(should/nit で直さなかったもの)」を、PR 本文の「確認したこと」にそのまま使えるよう箇条書きでまとめておく。
